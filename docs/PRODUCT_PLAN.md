### 功能完成與 Git 提交規則

使用者要求每個功能完成時 commit。此規則適用所有後續功能。

- 功能完成的條件為：實作完成、相關必要驗證通過、建立 commit；不累積多個已完成功能才一起提交。
- 以可獨立理解與驗證的功能為提交單位，使用清楚描述行為的 commit message。較大階段可拆成多個功能提交。
- PM 只維護規劃文件；工程師統一管理本機主要 checkout 的 Git staging／commit，避免兩個 session 同時操作 Git index。
- 提交範圍需檢查，包含該功能所需的程式、資產、測試與說明；保留 build 輸出及遠端快取的既有排除規則。未完成或尚未驗證的其他工作不混入已完成提交。
- 階段回報列出 commit hash、功能摘要與驗證結果；工程狀態文件記錄功能是否已提交。
- PM 檢查時 repo 尚無任何 commit。工程師先盤點已完成的 P0／P1／P2 與進行中的 P3，建立可驗證的初始基線；無法合理分離時不捏造歷史提交，說明實際基線範圍，再依本規則提交後續功能。
- 本機為 Git 主要來源，遠端仍是執行副本，沿用不傳 `.git/` 的單向同步方式。

P2 本批目標：讓兩名玩家看見直升機追擊，理解威脅，並能用既有騎乘操作避開一次可預警攻擊。

範圍與產品決策：

- 一架直升機，由 Server 在 Running 後啟動，進行 Chase → 攻擊預告 → 火箭攻擊 → Reposition 的循環。使用既有 GLB，不等待新模型。
- 先只做一種空對地火箭攻擊。預告階段顯示預計爆炸區域與剩餘時間；Rider chase view 可辨識威脅，Gunner 第一人稱另有攻擊方向提示。
- 顯示落點預告後，該次落點固定；不持續改成玩家當前位置，讓玩家能以轉向、踩踏或煞車離開危險區。預告時間、爆炸範圍、攻擊間隔及追擊距離由工程師暫定並集中設定。
- Server 決定 AI、火箭生成／移動、爆炸、命中及事件 ID；雙端顯示同一個威脅與結果，鏡頭／VFX 不裁決命中。
- 本批命中提供受擊提示與次數紀錄即可；生命值、完整勝敗、Gunner 鎖定反擊留到 P3／後續階段。
- 等待／Ready／倒數不攻擊，斷線／房間重設不殘留舊火箭或預告。保留雙人與開發用 solo 流程，不改已確認操作。

驗收證據：

1. 雙端 Ready／5 秒倒數後才進入追擊，兩端見到同一架直升機與一致的攻擊狀態。
2. 留在預告區的案例由 Server 判定命中；離開區域的案例可避開，預告不是必中的假提示。
3. 同一攻擊只生成／結算一次；重設後不延續上一局事件。
4. 一次受控 100 ms 固定延遲驗證及遠端 WASM 畫面證據，區分協定結果與真實畫面。既有 P1 Ready、角色權限與校正不退化。

工程師直接開始 P2，完成本批或遇到玩法取捨時回報 PM；技術細節自主決定，不開展 P3 或其他新玩法。

實作界線：

- 鎖定進度、可發射狀態、飛彈、生命值與結果皆由 Server 決定。Client 相機立即回應，HUD 可顯示預估但不得冒充權威已鎖定。
- 初版不做歷史命中回溯；Server 用當下世界與有效瞄準輸入判定，明確回饋未鎖定、目標離開、冷卻或缺彈的拒絕原因。固定延遲下驗證 HUD 與 Server 判定的差異，不宣告已解決所有延遲公平性。
- 有效輸入中斷不能無限維持鎖定，射手斷線／切座／房間重設清鎖定；不藉切座補滿耐久或彈藥。
- 玩家飛彈為遊戲化追蹤投射物，由 Server 模擬命中／超時／失效並只結算一次；沿用共用簡化碰撞資料與唯一請求／事件 ID。
- 移動、發射與結果事件在一般雙人及 solo 中一致。Finished 不再推進攻擊，重玩不帶入上局飛彈、鎖定或校正歷史。
- 預設畫面保留操作、鎖定、彈藥、冷卻、耐久與威脅提示；大量工程診斷改為開發開關，避免遮住瞄準視野。不要求重做完整 UI。

驗收：實際 WASM 畫面可旋轉座椅看見／瞄準直升機；維持瞄準完成鎖定並發射。受控測試涵蓋未鎖定拒絕、短暫偏離／清零、超距／遮蔽、重複請求／冷卻／缺彈、命中一次、勝敗與重新 Ready。一次固定 100 ms 雙端驗證須確認生命值、結果與事件一致，既有 P1／P2 不退化。

工程師直接開始 P3，參數集中可調；若可瞄準性、延遲判定或單人／重玩架構出現玩法衝突，先提供具體方案給 PM，其餘工作自主推進。

### P3 原型工程驗收通過，開放 P4

PM 已核對 `6b453a8`、工程狀態、`docs/verification/p3/` 驗證紀錄及三張 WASM 畫面。工程師回報 27 個測試、格式、Clippy、Native／WASM 與 release build 通過；固定 100 ms RTT 的雙端實際操作完成鎖定與三次飛彈命中，直升機耐久 100 → 66 → 32 → 0，雙端勝利事件 ID／Tick 一致，重新 Ready 後耐久、彈藥與倒數重設，solo 切座亦通過。接受 P3 原型工程交付；正式難度、局長與實體 GPU 手感未驗收。

P4 目標：讓 Rider 的路線選擇與 Gunner 的戰鬥形成完整短局，保留原本擊落勝利，另可沿路抵達逃脫終點。以下為 **PM 的可調原型方向，不是使用者已確認的正式關卡或平衡**。

範圍與產品決策：

- 先製作約 1.2 km、依序包含開闊河岸／橋下掩體／狹窄彎道的單一路線，沿用現有 GLB 與必要占位幾何。路段長度、彎曲程度與障礙配置由工程師在可騎乘前提下集中設定；不等待新模型，不以精準重建台北河岸為目標。
- 以共用關卡資料定義道路、簡化碰撞體、遮蔽物、起點、檢查點與終點；Client 場景、Rider 預測及 Server 權威使用相符資料。Server 保持 headless，不載入渲染素材。取消舊短跑道邊界對完整路線的不合理限制。
- 車體維持自由騎乘，不強制吸附中心線。彎道與狹窄段仍應容許現有腳踏車轉彎；可見護欄／障礙與碰撞相符，避免不可見牆或穿越捷徑。需要調整控制器時記錄具體可騎乘問題與必要改動。
- 橋下必須是有效掩體。必要橋面可用簡單幾何補足；Server 遮蔽資料同步阻擋射手鎖定、投射物與敵方攻擊視線。直升機不能穿越掩體；失去攻擊視線時改為追蹤／重新定位，不隔著橋面攻擊。已發射投射物先撞掩體則結算該次碰撞，不穿透造成車體傷害；橋下不能靠無限鎖定擊落被遮住的目標。
- 勝利條件暫定為「擊落直升機」或「依序通過路線檢查點並抵達逃脫終點」；Server 裁決並區分結果原因。同 Tick 車體耐久歸零仍以失敗優先。單純接近終點、逆向切入或漏掉檢查點不能完成逃脫。
- HUD 顯示目前區段及剩餘路程／終點方向，場景有可辨識終點。完成後沿用雙方重新 Ready／5 秒倒數，重設起點、路線進度、戰鬥與預測歷史。保留正常雙人與開發 solo 流程。
- 本批不新增障礙碰撞傷害、武器種類或正式 Lobby；3–5 分鐘仍是後續玩法調校目標，不以目前三發可擊落的測試配置宣告局長達標。大量診斷維持 F3 開關。

交付與 commit 單位：

1. 完整路線與共用碰撞配置：確認三段可連續騎乘、預測與 Server 碰撞一致，驗證後 commit。
2. 有效橋下掩體：確認敵我遮蔽、投射物碰撞及直升機重新定位，驗證後 commit。
3. 進度與逃脫勝利：確認順序檢查點、終點、雙端結果一致與重玩清零，驗證後 commit。

工程師可依依賴調整功能分界，但不要累積多個已驗證功能才統一提交。PM 文件亦由工程師統一提交，不由兩個 session 同時操作 Git index。

驗收證據：共用模擬／Server 測試涵蓋彎道與邊界碰撞、遮蔽清鎖定、掩體阻擋敵我投射物、漏檢查點／非法終點不勝利、正常完整逃脫及重玩清零。以固定 100 ms RTT 的雙端 WASM 確認區段畫面、有效掩體及逃脫事件一致；長路線可先用受控非渲染輸入驗證全程，再用瀏覽器驗證代表性區段，清楚區分工程證據與實際遊玩。另核對準星與鎖定圈同心且對應實際瞄準方向。既有擊落勝利、Ready、座位權限與 solo 不退化。

工程師直接開始 P4，完成各項功能即 commit，階段完成時提供 hash、實測路線長度、逃脫耗時與證據。若現有控制器無法合理通過彎道、掩體讓戰鬥無法繼續，或需要修改已確認操作，才提出方向問題給 PM；技術方案自主處理。

#### P5：房間、邀請、準備與重連

以下是 **PM 暫定產品方向**，工程師可自主選擇協定、UI 技術及檔案結構，不改既定騎乘／瞄準操作。

- 入口提供建立房間、輸入邀請碼／加入邀請網址；建立後顯示可複製的邀請網址與房間代碼。正式雙人不再一進頁面就自動搶占同一全域房間。沿用直接連線入口時須清楚區分開發用途。
- 同一 Server 先支援最多 4 個活躍房間，每房間獨立車體、AI、戰鬥、路線、事件與座位，跨房間不可互相操控或收到快照。無人在場且無保留席位的房間 10 分鐘後清理；上限集中設定，滿房／不存在／已被占用提供可理解訊息。
- 使用者已確認重設選單、不能依連線順序強制首位為 Rider，且只在開局前／結束後選角與互換，遊戲中固定座位。新加入先是房間成員、尚未選角，不可 Ready；未選角不是額外 Observer 遊戲角色，房間成員上限仍按必需座位容量管理。
- 角色選單使用 Rider／Gunner 兩張卡片，說明第三／第一人稱、騎乘／鎖定操作，呈現空席、自己或隊友選擇。任何人都可先選任一空席，由 Server 原子分配；不得搶占，不以房主或連線先後決定角色。
- 兩席都有人時提供「提出交換」，另一人可接受／拒絕；雙方同意後 Server 原子互換並清除雙方 Ready。請求暫定 15 秒過期；拒絕、離房、斷線、其他選角變更或倒數開始時撤銷，過期／重複回覆不得意外交換。交換請求待回覆時暫停開始倒數。單方選擇被占用角色不能直接搶位。
- UI 明確顯示 Ready 前應先選角，交換成功後重新準備；已在 Countdown 可先取消 Ready 回準備階段再交換。Running／暫停／恢復倒數不開放正式換座，Finished 可為下一局交換。開發 solo 的 V 保留且不影響其他房間。
- Lobby 用可點擊 UI 呈現座位、連線與 Ready，顯示操作說明及隊友等待狀態；R 保留快捷操作。Ready 可以取消；開局倒數中取消 Ready 或斷線即取消倒數，清除雙方 Ready，兩人重新準備後由 Server 重新倒數完整 5 秒。倒數前不接受正式騎乘或攻擊。
- Running 任一必需座位連線失效時，由 Server 暫停該房間。清除按住輸入、鎖定、預告及飛行中的投射物，保留車體位置／耐久、直升機耐久、彈藥與路線進度；已花費彈藥不退還。暫停期間不移動、不受傷、不推進 AI／武器冷卻。其他房間照常運作。
- 斷線席位保留 30 秒（以牆鐘計時），提供房間／玩家專屬、不可猜測的 Reconnect Token，僅存於該分頁的 session storage；邀請網址不得包含它。刷新／短斷線可自動重連回原房間及原席位，不接受 token 跨房間或同時控制兩條連線。
- 重連成功後仍暫停，兩人重新 Ready，再走 5 秒恢復倒數，保留本局狀態，不重補耐久／彈藥。倒數中再次斷線仍回暫停；恢復後重新開始追擊與完整攻擊預告，避免瞬間受傷，Client 重建預測與插值歷史、舊連線輸入不得復活。
- 超過保留期限或 Running 主動離房時，本局結束並顯示「隊友離線／離開，對局中止」，不算擊落或逃脫勝利。釋放席位，留下的玩家可邀請新人重新 Ready 開新局。等待／Finished 可正常離房；Server 重啟後提示原對局不存在，允許回入口重新加入。
- 結果頁區分逃脫、擊落、耐久歸零與中止，提供再準備／離房。HUD 聚焦耐久、彈藥／鎖定、威脅與路線，連線中斷不得顯示遊戲仍在正常進行。完整文案使用繁體中文；既有字型不支援時由工程師加入合適字型或以可讀的網頁 UI 呈現。

P5 建議提交單位：房間與邀請／座位 UI、取消 Ready 與生命周期、暫停與重連、結果與操作 HUD。每項必要驗證後 commit；完成 P5 後直接進 P6。

P5 驗收：至少兩房間同時運作及隔離；滿房／錯碼／搶座競爭；第一位可選 Gunner、第二位選 Rider，未選角不能 Ready；交換同意／拒絕／過期／競態／重複回覆、交換後清 Ready、Running 不換座、Finished 互換；Ready 取消、倒數斷線、Running 兩種座位斷線、30 秒內恢復／逾期中止、刷新、無效或跨房間 token、舊 socket 輸入與重複連線；重連不補給、不重複命中、不跳過檢查點。一次真實雙 WASM 的邀請→選角／交換→Ready→斷線→重連→恢復→結果／重玩操作，記錄房間／事件／Tick，保留 solo 回歸。

#### P6：網路、效能與瀏覽器驗證及必要修正

以目前可用環境自主完成工程驗證，目標先定為桌面鍵鼠、WebGL2、1280 × 720 的 Chrome／Chromium 與 Firefox；手機與 Safari 未納入本批承諾。瀏覽器版本、GPU、環境、測試工具與注入層級須記錄，缺少可測環境時列為未驗收，不阻止其他驗證。

- 網路矩陣：0／50／100／200 ms RTT；另外 100／200 ms RTT 搭配每方向 ±20 ms jitter，使用可重現種子與有序排程。輸入涵蓋踩踏／左右轉／煞車、射手持續瞄準與發射、掩體及重連。分別記錄相同 Tick 位置／yaw 誤差、收斂時間、history miss、Ack backlog、Gunner 狀態年齡／額外校正與事件一致性，不能只看跨 Tick 距離。
- 封包遺失另測 1% 與短斷線：若能使用僅限測試連線的隔離 network namespace／netem，記錄實際 TCP 重傳與 HOL 效應，不修改主機全域網路。工具或權限不足時仍完成 jitter／重連測試，清楚標明 packet loss 未驗；丟掉應用層訊息不能冒充 TCP packet loss。
- 原型工程門檻：雙端結果／唯一事件一致，無越權、重複傷害或幽靈輸入；受控 15／30／60 FPS 與 jitter 測試，放開／煞車並待快照追上後，同 Tick 位置誤差於 1 秒內連續三份快照低於 2 cm，Ack 排空，非刻意長斷線不得 history miss。未達標先分析與修正，再重驗受影響範圍，不以抬高門檻掩蓋問題。
- 以 4 房間／8 玩家同步運行至少 10 分鐘測 Server：固定 60 Hz，記錄 tick duration p50／p95／p99、快照 bytes／秒、實際頻率、記憶體與錯誤。原型目標 p95 < 8 ms、p99 < 16.7 ms，沒有隨運行持續增加的未清理房間／Session／投射物；達不到則先解決具體瓶頸，不新增無關框架。
- Browser 各完成載入、pointer lock、左右轉、自由觀看／回正、右鍵鎖定／單發、視窗失焦清輸入、邀請／Ready／重連及勝敗重玩冒煙；沒有 runtime exception。保留一次完整路線與擊落回歸，不必每個矩陣重跑整條路線。
- 有硬體 GPU 的環境才量測實際畫面 FPS／frame time、輸入至本地相機回應、快速轉向時 Gunner 的非預期跳動；先記錄硬體與基線，原型目標 p95 frame time < 33.3 ms、無持續影響瞄準的凍結。SwiftShader／非渲染測試不能宣告此門檻通過；無硬體環境時交付剩餘實機驗收清單與可直接重現方式。
- 所有修正以功能或具體缺陷為單位 commit，測試工具／驗證報告亦提交。最後整理 `docs/verification/p6/`、支援範圍、已通過／未驗／已知限制、服務版本及本機／遠端同步結果，PM 依證據判定完成範圍，不把原型數值等同正式玩家平衡。

工程師依序自主推進 A／D → P5 → P6；例行技術問題直接處理，只有改變已確認操作、超出此範圍或出現重要產品取捨時找 PM。PM 不實作程式、不與工程師並行操作 Git index。

車體移動對射手視角的影響屬玩法；網路插值或校正導致的額外跳動屬體驗問題，驗收時需分開觀察。

## 現況與近期目標

交接時已具備 Cargo workspace、Client／Headless Server 啟動骨架，以及 15 個基本 GLB 與掛點資料。素材格式已有驗證，但尚未完成遊戲內場景接入、操作、網路或 Lobby。實際進度以工程師的狀態文件及可重現驗證為準。

目前 P0–P4 原型已交付，近期目標為 **修正 A／D，完成 P5 房間／重連與 P6 工程驗證**；有效工作指示及驗收以本文件上方最新階段決策為準。下方保留初始工作順序作為規劃背景。

## 工程工作順序與驗收

### 第一批：P0，本地騎乘與鏡頭原型

工程師可先開始這批工作。

範圍：簡單跑道、基本載具與障礙物、Rider 操控、第三人稱鏡頭；另提供開發用方式檢視 Gunner 第一人稱與旋轉後座，方便在接網路前驗證視角。

驗收情境：

1. Native 與瀏覽器可啟動場景，遊戲中可辨識車體、跑道與障礙。
2. Rider 按住左鍵踩踏，放開停止踩踏；空白鍵煞車，且與停止踩踏的行為不同。
3. Rider 按住右鍵轉視角，車體方向不因觀看而自動改變；放開後自動回到 chase view。
4. 自由觀看時仍可踩踏、煞車；離開操作焦點後不殘留按住狀態。
5. 原型能轉向、碰撞；暫定按鍵與碰撞行為須有說明。
6. Gunner 視角位於第一人稱視線位置，旋轉後座不使角色離開車體；車體位移／轉向會影響射手視角。

此批交付應包含操作說明、重現步驟與瀏覽器實測結果。只通過編譯不代表完成產品驗收。

### 第二批：P1，雙人共乘與開局流程

範圍：Dedicated Server、最小單房間／座位分配、輸入同步與權威校正、雙端角色視角、Ready 與倒數。完整建房邀請 UI 留到後續。

驗收情境：

1. 兩個瀏覽器可連線至同一 Room，分別佔用 Rider 與 Gunner，並看到同一台腳踏車的移動結果。
2. 只有 Rider 的騎乘輸入控制車體；Gunner 的觀看／座椅旋轉不控制車體方向。
3. 缺少必需座位或任何一人尚未 Ready 時，不開始倒數。
4. 兩人都 Ready 後，兩端顯示 Server 控制的 5 秒倒數；倒數結束才進入正式騎乘／戰鬥狀態。
5. Rider 的第三人稱自由觀看與 Gunner 的第一人稱觀看在連線情境下保持既定操作語意。
6. 在 RTT 50／100／200 ms 下記錄車體校正與射手視角表現，列明 Jitter／Loss 設定、裝置、瀏覽器及已知問題；特別區分正常車體帶動與額外網路跳動。

此批先取得可比較的體驗基線，尚不宣告達成 P6 的最終效能／相容性要求。若明顯延遲或跳動妨礙操作，先處理核心體驗再擴充戰鬥內容。

### 後續：P2／P3，追擊與鎖定戰鬥

加入一架直升機與可預警攻擊；Gunner 持續右鍵瞄準才能累積鎖定，Server 拒絕未完成鎖定的發射，兩端看到一致的發射與傷害結果。

進入這批前，需定案鎖定取得／解除規則，以及延遲下 Client 預估鎖定與 Server 判定差異的產品處理方式。

### 後續：P4／P5／P6，完整短局

補齊河濱路線、完整 Lobby／重連／HUD、勝敗與重玩，最後以指定裝置和網路條件做相容性與體驗驗收。完整關卡配置前需確認勝利條件是逃脫、擊落，或兩者的組合。

## 決策分類

### 工程師可自主決定

- 符合既定 headless、WASM 與權威模型的技術組合、程式拆分、固定更新與網路整合方式。
- GLB 接入、占位幾何、碰撞資料、診斷介面及測試工具。
- 不改變既定操作語意的鏡頭平滑、阻力與其他可調整原型參數。
- 尚未指定的轉向／發射按鍵可採用可更換的原型配置，註明「暫定」，保留後續調整能力。

以上原型選擇須記錄，但不需要例行請 PM 核准，也不能標記為使用者已確認。

### 需要 PM 思考方向

| 決策 | 最晚需要處理的時點 |
|---|---|
| 車手轉向按鍵、射手發射按鍵的正式配置 | 操作原型體驗後、正式操作說明前 |
| 後座旋轉範圍、瞄準俯仰限制、傾斜如何影響視角 | P0／P1 鏡頭驗收 |
| 鎖定區域、累積時間、離開區域／放開右鍵／遮蔽後的處理 | P3 前 |
| Client 顯示已鎖定但 Server 尚未允許發射的體驗 | P3 前 |
| 倒數中取消 Ready／斷線，以及 Running 中斷線的玩法 | P1 生命週期驗收與 P5 前 |
| 逃脫／擊落的勝利條件、路線長度與局長 | P4 完整關卡配置前 |
| 指定目標裝置、最低體驗與效能門檻 | 原型量測後、P6 最終驗收前 |

其他介入觸發點：需求衝突、技術限制迫使修改已確認玩法、範圍需要取捨，或階段驗收顯示核心合作體驗不成立。

需要 PM 決策時，只暫緩依賴該決策的工作；可繼續其他已明確且不受影響的工作。
